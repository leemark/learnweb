# LearnWeb code and learner experience audit

Audit date: October 6, 2026

Site: [learnweb.cc](https://learnweb.cc/)

Starting revision: `059cd77` on `codex/learnweb-quality-remediation`

Review and integration: lead agent, with bounded Luna xhigh implementation and testing

## Executive assessment

LearnWeb has a strong identity and a useful product underneath it: six learning
paths, 36 project-based lessons, real workspaces, saved progress, and readable
static lesson pages. The right improvement was to make learning easier to start,
continue, and complete while fixing defects that could undermine trust. A new
framework or wholesale visual redesign would not have addressed those problems.

This pass improves the actual learner journey, not just the landing page. A new
learner can start in one action; a returning learner can resume from the hero;
lessons have clear section navigation and completion requirements; mobile editors
have usable space; search returns relevant, complete results; and backup failures
no longer silently leave a partially imported state in the tested failure case.

The changes belong to the existing feature branch and [draft pull request 5](https://github.com/leemark/learnweb/pull/5).
They are not a claim that the public site has been updated. Production was still
serving the older interface during this audit. Merging and publishing remain
separate release steps.

## Findings and changes

Priority 1 means a problem affecting core use, saved work, or reliable execution.
Priority 2 means meaningful clarity, accessibility, or instructional quality.

| Priority | Finding | Resolution in this branch |
|---|---|---|
| 1 | Re-running learner JavaScript reused a global environment. A second top-level `const` could fail, and old timers could affect later runs. | Every run gets a fresh isolated document. Run-specific messages reject stale heartbeats. Repeated runs and Stop do not add browser-history entries. |
| 1 | Backup restore could write some keys, fail on another, and still replace the current session's work. | Validate first, confirm replacement, retain snapshots, commit memory after storage succeeds, and roll back previously written keys on failure. Persistent errors explain storage problems. |
| 1 | Mobile lesson code editors could collapse to a few lines above a tall preview. | Set a usable minimum editor height and reserve a separate line for the input-limit description. |
| 1 | Section jumps could scroll the outer lesson dialog and hide its close controls. | Only the reading pane scrolls. The dialog clips outer overflow; the header stays visible during section navigation and editor focus. |
| 1 | The app and its external code runner could use different protocol versions after deployment. | Pin the production runner to immutable commit `484458407cba51578baac9307dd707e25770fa0a`; integrity checks reject a mutable production runner URL. |
| 2 | The homepage offered several competing starting points and buried returning-learner continuity. | A primary Start learning action opens Foundations directly. It becomes Continue learning or Review lesson as appropriate. Browsing and placement remain secondary options. |
| 2 | Long lessons required repeated scrolling to reach work, checks, or notes. | Sticky Read, Build, Check, and Notes shortcuts, focused headings, tighter spacing, and visible mobile lesson position. |
| 2 | Learners could encounter an unexplained disabled completion button or submit an unanswered quiz without useful direction. | A completion checklist names the two requirements; missing answers receive feedback and focus; completion offers the next incomplete lesson. |
| 2 | Search over-ranked broad path terms, required contiguous phrases, capped results, and discarded the query on close. | Weighted title/detail/body matching, multiple search terms, all matching results, retained queries, useful empty states, and arrow/Enter/Escape behavior. |
| 2 | Import controls looked actionable but were not normal keyboard-focusable buttons. | Both import entry points are buttons, with clear replacement wording and a file chooser reachable by keyboard. |
| 2 | Typed input could exceed the limits accepted by saved-work validation. | Visible, accessible descriptions and native limits: 500,000 characters per code input and 100,000 per note or record response. |
| 2 | Static quiz options were numbered while revealed answers referred to letters. | Lettered options and the actual correct option text in the reveal, enforced by generator checks. |
| 2 | A password example lacked a proper label; an enhancement example referenced an undefined handler and had a duplicate quiz concept. | Associated label, a self-contained safe DOM example with an honest no-JavaScript explanation, and a distinct second question. |
| 2 | Horizontal code examples could not be reached and scrolled by keyboard. | Focusable, named code-example regions in interactive and generated lessons. |
| 2 | WebKit could retain oversized quiz legends after a narrow-screen resize. | Native fieldset flow and bounded legend width replace the problematic grid layout. |
| 2 | The update banner used a dark surface but inherited dark text and accents in the light theme. | Explicit surface text and scoped bright tokens keep the message and controls readable in both themes. Both-theme checks now include the visible banner. |

## Design and usability judgment

Keep the dark editorial identity, restrained accent colors, path cards, and
project-first approach. They make the site recognizable. The most important
hierarchy is now functional: start or resume, understand the lesson, build the
artifact, check understanding, then continue.

The lesson header and section shortcuts remain available on small screens. The
mobile editor is now a usable workspace rather than a sliver above the preview.
The existing local-first model also remains intact: no account wall, new tracking
service, notification funnel, or artificial streak mechanic was added.

There is still room to improve small secondary text and validate the amount of
instruction shown before the first task. That judgment should come from watching
beginners use the tool, rather than continuing to rearrange a working interface
without learner evidence.

## Code quality and data safety

The application remains dependency-light and progressively enhanced. Changes are
concentrated in the existing renderer, curriculum generator, styles, and browser
checks. No production dependency, new service, or framework was introduced.

Preview messages are bound to the expected window and run identifier. Learner
scripts remain in a cross-origin sandbox without same-origin privileges or modal
dialogs. Closing a lesson disposes of its preview work. Tests cover repeat runs,
old timer disposal, normal long-running code, stale messages, and browser history.

Backup tests inject a storage error after earlier writes have succeeded. They
verify the original raw keys, visible progress, exported in-memory values, and
state after reload. This is recovery logic around multiple local-storage keys,
not a database transaction: if the browser prevents rollback writes too, the app
warns the learner and retains the prior in-memory state. Local-only work still
needs an exported backup to survive browser-data deletion or device loss.

The October dependency audit returned zero published vulnerabilities for the
locked dependency tree. That result is not a penetration-test certification.
Existing checks also exercise malformed URLs, traversal rejection in the local
server, error handling, and exclusion of private learner content from analytics.

The main application file is large, but splitting it solely for appearances would
add regression risk. Extract modules when a concrete feature or measured loading
cost justifies it; keep the curriculum as the single source for interactive and
static lessons.

## Content and discoverability

The technical foundation is sound: 36 lesson pages, six path pages, and a learning
hub have real text, canonical URLs, semantic headings, and structured data. All
45 sitemap URLs and 49 unique internal link targets resolved successfully in the
local release candidate. The primary learning link also reached a readable lesson
with JavaScript disabled.

The strongest remaining content improvement is deeper worked evidence: a complete
example artifact, a short explanation of why it meets the definition of done, and
nearby links to authoritative references. Prioritize the beginner lessons and the
first lesson of each advanced path. A correct small example is more valuable than
another broad introductory paragraph.

For AI-assisted discovery, prioritize the same qualities: accessible text,
descriptive internal links, accurate structured data, clear authorship, and useful
answers supported by examples. Google does not require a special AI file or
special AI schema for its search features. No speculative discovery file or schema
was added. See [Google's guidance on AI features](https://developers.google.com/search/docs/appearance/ai-features).

After publication, verify indexing and actual queries in Search Console. The
presence of metadata and structured data does not prove indexing, ranking, rich
results, or citation by an answer engine. The curriculum's August release label
was not advanced merely to make the site look freshly reviewed; this pass contains
targeted instructional corrections, not a new factual certification of every topic.

This is a simulated mobile test of the local development server, which serves
uncompressed source files. It is not a production Core Web Vitals measurement or
a controlled before-and-after performance comparison. Accessibility 100 also
means only the checks Lighthouse can automate.

Render-blocking font CSS and the application stylesheet remain the clearest
loading opportunities; Lighthouse estimated roughly 1.45 seconds of potential
savings from render-blocking requests. Treat that estimate as diagnostic, not an
additive or guaranteed speedup. Keep the current typography unless a measured
self-hosted or reduced-font strategy improves loading without destabilizing layout.

Source payloads are approximately 46 KB HTML, 94 KB application JavaScript,
119 KB curriculum JavaScript, and 73 KB CSS. Locally calculated gzip equivalents
are approximately 12, 23, 39, and 15 KB respectively; those figures do not establish
the production server's transfer settings. Lazy lesson-data loading is an option
if production measurements show the initial module graph is a meaningful bottleneck.

For a release decision, collect field LCP, INP, and CLS, or use production lab tests
as clearly labeled interim evidence. [Core Web Vitals guidance](https://web.dev/articles/vitals)
distinguishes real-user measurement from laboratory diagnostics.

## Verification coverage

- Browser smoke suites: Chromium, Firefox, and WebKit. Coverage includes learning
  paths, navigation history, completion gates, workspaces, notes, search, placement,
  backups, storage errors, and runner outages.
- Targeted resilience suites: all three browser engines, including failed-import
  recovery, export/reload consistency, fresh code execution, and input limits.
- Learner-journey checks: direct entry, resume, completion, keyboard search/import,
  section focus, usable editor height, and reflow at 320, 390, 768, and 1440 pixels.
- Automated accessibility checks: both themes, mobile and desktop home/lesson
  states, code workspaces, and representative static lesson output.
- All 43 generated learning pages: browser-rendered HTTP status, canonical URL,
  main heading, static quiz labeling, and narrow-screen overflow checks.
- Generator/integrity checks, build, dependency audit, and whitespace checks.

The expanded learner-journey suite passes in Chromium and Firefox. Its WebKit
run reaches the desktop theme scan but reports foreground colors inconsistent
with subsequent live computed styles and rendered screenshots. Mobile checks
pass, and the ordinary WebKit smoke and resilience suites pass. The expanded
WebKit suite is therefore **not recorded as passing**; confirm desktop theme
switching in real Safari before closing this accessibility verification gap.
No contrast rule is disabled to hide this result.

Repeatable commands are documented in `README.md`. `npm run test:quality` adds the
new journey and recovery tests to CI. Local screenshots and Lighthouse evidence
are retained under the ignored `output/playwright/` directory.

These checks do not replace physical iOS/Android testing, VoiceOver/NVDA/TalkBack
use, learner research, or a full manual WCAG review. The synchronous infinite-loop
probe is deliberately separate because headless browsers do not reliably isolate
iframe processes. Firefox and WebKit also retain documented offline-emulation
limitations; Chromium verifies the offline fallback contract. Browser-engine
emulation is not evidence that every physical device behaves identically.

## Remaining priorities

1. **Release verification.** Review and merge the existing pull request, then check
   the actual published interface, static URLs, preview runner, service-worker
   update path, and production performance. A pushed branch is not a deployment.
2. **Observe beginner use.** Ask a small set of new learners to start, complete one
   lesson, leave, and return. Record where they hesitate and whether their artifact
   demonstrates the intended skill. Improve those points before adding engagement
   features. Existing progress/resume behavior is a useful retention foundation,
   not proof of retention improvement.
3. **Reduce external runner risk.** The immutable CDN pin prevents protocol drift,
   but it does not remove third-party availability risk. A separately isolated,
   first-party runner origin is the long-term operational improvement. Keep the
   security boundary; do not move untrusted execution onto the application origin.
   [RawGitHack's documentation](https://raw.githack.com/) describes its production
   commit-pinned endpoint and lack of an uptime guarantee.
4. **Deepen instructional evidence.** Add reviewed finished artifacts, targeted
   primary-source references, and a complete beginner publishing walkthrough.
5. **Measure production access and discovery.** Resolve the WebKit theme-scan
   discrepancy and validate real assistive-technology
   journeys, field performance, indexing, and search queries after release. Review
   hosting security headers against the actual provider before changing policy;
   avoid an untested policy that breaks the runner, fonts, or offline behavior.

No claim is made that an audit can guarantee rankings, answer-engine inclusion,
retention, or universal accessibility. This branch substantially improves the
observed learning experience and adds repeatable protection for the highest-risk
behaviors, while leaving the remaining product and release decisions explicit.
